# V0.8.4 PPC64 ELF multi-segment & relative relocation proof

V0.8.4 extends the **original self-authored PowerPC64 homebrew ELF**. It introduces a second PT_LOAD segment for writable initialized data/BSS, applies one genuine `R_PPC64_RELATIVE` relocation, and then statically translates the program's instructions into a Windows x64 native EXE.

This is **not** a native PS3 game port. No retail executable, encrypted SELF, firmware or proprietary assets are included.

## Implemented, strictly bounded ELF subset

- Big-endian `ELF64`, `e_machine=21`, `ET_EXEC`, single RX code PT_LOAD (maximum 4 KiB).
- Up to three non-overlapping RW data PT_LOADs (each memory size maximum 4 KiB), all confined to fictional demo guest RAM `0x2000..0x11fff`.
- Every PT_LOAD is checked for file bounds, `p_filesz <= p_memsz`, alignment and virtual-address overlap.
- Initialized data bytes copied into the guest sandbox **before translated code starts**; `p_memsz - p_filesz` is zero-initialized BSS.
- Section-header table validation and bounded `SHT_RELA` records (24 bytes each, maximum 32).
- **Only** `R_PPC64_RELATIVE` type 22, symbol index 0, is accepted. The fixed `ET_EXEC` demo uses load bias `B=0`, so the relocated 64-bit value is `B+A`; the relocation target must fall inside an RW data segment, and both address and result must be inside the demo's guest sandbox. The write uses the existing big-endian checked guest-store helper.
- Unknown relocation types, symbol-based imports, `SHT_REL`, malformed tables, overlapping virtual memory, out-of-range targets and unsupported instruction opcodes are rejected **before any C++ output is written**.

The full PowerPC64 ELF ABI, relocatable shared objects, TLS/PLT, dynamic linking, permission enforcement, program interpreter and PS3 OS memory system are **not** implemented. This narrow subset may reject valid real-world ELF files.

## Native execution evidence

The generated original ELF now has two program segments:

| Segment | Guest virtual address | File bytes | Memory bytes | Purpose |
| --- | --- | --- | --- | --- |
| RX code | 0x10000 | 144 | 144 | Original PPC64 instructions with nested calls and guest stack |
| RW data | 0x3000 | 16 | 64 | Relocated pointer, initialized 0xAB byte, and zero-filled BSS |

The ELF contains a RELA record `R_PPC64_RELATIVE` at `0x3000` with addend `0x2000`, yielding a pointer to mapped demo RAM. Translated code loads the pointer from the separate data segment, stores its arithmetic result through that pointer, reloads the value, reads the initialized `0xAB` byte, and verifies zero-filled BSS.

Run `LumavunPPUHomebrewPort.exe` in a terminal. Expected:

```text
PPU_HOMEBREW_RESULT=15
PPU_GUEST_BE_BYTES=18,52
PPU_STACK_RESTORED=1
PPU_ELF_RELOCATED=1
```

The Windows build artifact continues to include original `PPU_HOMEBREW.ELF`, generated `LumavunPPUHomebrewPort.cpp`, and native `LumavunPPUHomebrewPort.exe`.

## Automated acceptance gates

- MSVC CTest: `native_ppu_elf_relative` runs the native executable and requires `PPU_ELF_RELOCATED=1`.
- Python tests check independent PT_LOAD segments, initialized bytes, BSS, RELA records, mismatched type/symbol, corrupt section header, invalid data location, code/data overlap, and source-output fail-closed behavior.
- Existing PPC stack/memory safety tests and all previous PS1, PS2/PS3 inspector, native launcher and pipeline tests remain active.

## Still blocked

Gundam Reborn is not playable. Work is still needed on real-title identification, executable and module inventory, complete ABI, memory protection, dynamic relocations/imports, much wider PPU instruction coverage, SPU tasks, RSX graphics, CellOS services and user-interface/audio/save paths. A green homebrew CI **cannot** establish compatibility with a PS3 game.
